# 两周 MVP 验证清单

目标：完成一个“事件 → 角色状态 → 桌宠反馈 → 外壳候选”的可记录闭环，而不是完成最终产品。

## 第 1 周：设备与数据底座

- [ ] 采购/确认 ESP-VoCat v1.2 完整成品（已焊接、屏幕/双麦/扬声器/电池齐全），并向卖家索取版本和固件信息。
- [ ] 固定 ESP-CLAW 仓库 commit/tag，保存 README、许可证和刷机说明。
- [ ] 烧录并运行基础固件。
- [ ] 单项测试屏幕、麦克风、扬声器、IMU、base yaw 和 USB/磁吸接口；触摸与 NFC 作为可选扩展，暂不把摄像头或 pitch 作为通过条件。
- [ ] 记录每项测试的接线、固件版本、延迟、失败现象和照片。
- [ ] 建立 `shell-interface-v1` 的硬件测量表，制作简化包络模型。
- [ ] 用 DeskBot Chat 建立一个最小角色、世界规则和一条可重复对话脚本；RisuAI/SillyTavern 只做机制对照。

## 第 2 周：闭环与首件

- [ ] 建立 DeskBot `/api/chat` 与 `/api/event` 主线；对照实验需要时再接 RisuAI/SillyTavern 适配器。
- [ ] 建立角色状态服务，保存 revision、evidence 和规则版本。
- [ ] 先用 `fake-device` 完成 `device.hello`、`speak`、`render.expression` 和 ACK 幂等；再通过桥接层发送给 ESP-CLAW。
- [ ] 完成至少 3 种状态反馈：表情/屏幕、语音风格、云台动作。
- [ ] 设计并打印一个只验证接口的“工程壳”，不追求造型。
- [ ] 完成 5 次装配/拆卸和一次云台全行程测试。
- [ ] 如已安装 NFC，完成一次 `shell.install.detected` 到 `shell.install.confirmed` 的去重测试。
- [ ] 手动生成一个 `shell_trigger.status = candidate` 记录。
- [ ] 写下端到端延迟、失败率、证据可追溯性和待解决问题。

## 每次实验必须记录

```text
日期与操作者：
硬件版本 / 固件 commit：
DeskBot Service / 模型 / 规则版本：
可选对照项目 / 适配器版本（未启用填无）：
输入事件与来源：
状态 revision：
使用的 evidence ID：
设备反馈：
延迟（输入到反馈）：
机械问题：
结果：通过 / 部分通过 / 失败
照片、视频或日志路径：
```

## 两周结束时的通过标准

- 同一输入脚本可以重复得到结构合法的 `role-state.v1`。
- 至少一个状态变化能可靠驱动设备反馈。
- 工程壳能在不拆主板和线缆的情况下完成 5 次装配/拆卸。
- 至少一个外壳候选触发有明确证据、阈值和日志。
