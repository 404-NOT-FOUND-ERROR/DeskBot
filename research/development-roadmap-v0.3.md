## 2026-09-18 叙事与 NPC 增量

首发 NPC 已从固定台词推进到 Persona Agent v0.1：作者用 `research/npcs/*.md` 描述人物的欲望、爱憎、口癖、触发点与边界，Node 将当前 Scene、关系和共同经历编译成受限提示词，LLM 只生成当面台词，世界写入仍走 canonical mutation。地点和 Scene 同步改为桌边潮玩生活语汇，减少“世界规则说明”感。

这段记录属于早期增量说明，不再代表当前 P3/P4 状态。真实 DeepSeek 人物样本、`role-state.v1` 阶段档案、NPC 有限目标和形态方向提案已分别接入；当前仍不能把有限规则闭环称作开放式自主生命体，跨天主动性和真实形态落地仍需后续验收。

世界环境、用户输入和角色状态绝不混成一团：世界事件有自己的规则；用户提供方向信号；喵呜只能经可追溯规则形成选择、记忆和阶段变化。

## 2026-09-27 真实墙钟接入

持续世界现在有了可恢复的真实时间锚点：SQLite 运行时在启动和每分钟调度时把已过去的整分钟映射为 `advance_time` mutation，最多每轮追赶 120 分钟，marker 保留未处理区间与秒级余数。稳定 event ID、先写待执行 marker 再写 canonical ledger、最后提交完成 marker，使服务异常退出后能重放而不重复推进。没有持久化的测试实例不启用该行为。它只推进逻辑时间，不替代世界生活引擎，也不把真实时间问题直接塞给角色；下一步仍是以人工跨天回访验证 Scene/NPC/关系的可感知后果。

## 2026-09-17 持续世界空间层增量

已加入首个 canonical 聚形域地图：聚形域桌面、潮痕旧路、低语集市、逆光林地、回声水岸。地点坐标只供客户端布局；地点事实、邻接路线、旅行耗时、NPC 位置、当前地点和事件封路均归 Node canonical world 所有。`GET /api/world/map` 是派生读模型，`POST /api/world/travel` 必须转成 `move_protagonist` mutation，成功旅行推进逻辑时间并产生第一人称抵达反馈。LLM 文字、浏览器 DOM 和用户一句命令都不能绕过规则移动角色。

Web 地图支持点击地点聚焦、区分当前/可达/需中转地点、显示 NPC 与事件影响，并从相邻地点发起旅行。在空间骨架之上，世界自动生活 V1 已完成：正式服务按 30 分钟真实时间槽，根据当前位置、逻辑时间段、世界线和天气选择有限 Scene；Scene 和 NPC 行动先写 canonical mutation，再进入故事窗、地图和 prompt。网页刷新本身不推进世界。

下一阶段按以下顺序补强世界存在感：

1. 地点生活切片（V2 已完成）：五个地点各有三条有限日常；当前 Scene、感官细节、未发生机会和最近历史可回放。同事件可跨槽延续，最近模板有冷却，不再每半小时机械重播。下一步把世界线结果接成真正的 Scene 因果分支。
2. NPC 在地行动（V2 已完成）：三个首发 NPC 有档案、当前行动、同地点相遇面板和六种受限互动；有限目标已能沿相邻地图移动，内置日程会形成抵达与离开。下一步扩展多步等待、失败、改道与支线后果。
3. 主线/支线场景：正在发生的事件绑定地点、参与者、机会和未解钩子，形成 Character.AI 式第一人称经历，而不是后台世界摘要。
4. 地图事件反馈：封路、开放新路径、季节变化必须由世界 mutation 产生，并保留历史；用户只能影响选择方向，不能直接覆写世界规律。
5. 长期演化闭环：经历和关系只作为角色方向证据，经候选、试行和明确阶段决策后才影响身份、表达、声音、表情与未来外壳。

验收门槛：旅行与 NPC 行动可回放且重启一致；用户/LLM 无法越权移动；页面在桌面和手机不遮挡主对话；同一地点至少出现三种由状态驱动的具体生活切片，且不会每轮机械播报。

客户端方向已修订为“Character.AI 沉浸故事 × WorldOS 持续世界”：默认第一屏是像素奇幻地图而不是研究仪表盘；喵呜的第一人称故事浮在左上，输入固定在底部，其他系统作为游戏面板叠加。地点已加入按需 Scene 锚点、感官线索和未发生的 possible beats；当前生活 Scene 和同地 NPC 已进入同一检索层。页面加入“人物”入口、此地横排角色、首次相遇自动呼出、关系状态与受限互动；NPC 回应独立署名，不伪装为喵呜。

方法参考：Character.AI 的 [Lorebooks](https://support.character.ai/hc/en-us/articles/52739596326811-Lorebooks)、[Scene Creation](https://support.character.ai/hc/en-us/articles/41918454359451-Scene-Creation-Quickstart-Guide) 与 [Creator Guide](https://support.character.ai/hc/en-us/articles/50608794517915-1-Welcome-to-the-Creator-Guide)。只迁移“常驻人格、按需知识、当前场景”三层分工，不把生成文本当作世界事实。

**G3：** 记录过的关系事实可跨会话正确回调并可更正；未记录的不被声称记得；主动性有理由、可关闭、不过量。

## P3.1：有限世界自动生活（有限闭环已实现，下一轮扩展目标）

**目的：** 用户离开桌面后，小镇仍按规则生活，并在用户回来时留下可追溯的共同经历。

实施顺序固定为：逻辑时间推进 -> NPC 日程/目标决策 -> 合法相邻行动 -> canonical mutation -> Scene/地点后果 -> 喵呜观察、回调和形成候选证据。每一轮只推进有限步骤，失败、等待、阻断和重启都要可解释；自动经历不能直接写入用户确认记忆，也不能单句改变角色阶段。

当前有限闭环已覆盖：一名 NPC 的日程移动、地点 Scene 延续、世界线结果分支和可在对话中引用的共同经历，并能跨日回放、重启恢复和幂等重试。下一轮校准主动打扰冷却、事件后果和关系趋势，之后再把真实天气/新闻等外部源接入 evidence，而不是直接播报或改写世界。

真实墙钟已接入启动/每分钟调度：服务重新上线后不会把停机时间吞掉，而会以有上限、可重放的时间 mutation 追赶；这解决“离开桌面后世界完全停住”的基础缺口，但不等于已经证明世界会自发产生有趣故事。

P3.1 的自动化门槛已满足：重启后状态一致、行动有 mutation/evidence ID、世界事实与表达分离、用户只能影响选择方向。人工跨天体验和路线视觉验收仍需继续；P4 的阶段档案已可供这些体验验收使用，在真实表达和外壳生成前仍不能把有限规则当作长期生命感证据。

## P4：角色方向试行与阶段档案（1-2 周，有限试行已实现）

**目的：** 真正做出“它会变成不同的它”，而不是换一份提示词。

建立 `observing -> candidate -> proposed -> trying -> accepted/rejected/deferred -> archived` 状态机。服务端规则闭环已实现：多源 evidence 聚合后持久化候选与提案；候选/同步运行保存在 SQLite；只有成功的用户聊天回合生成中性试行观察；相同 event/fingerprint 重放幂等；用户选择 `try/later/reject`，并在有界窗口后明确接受/拒绝/延后。accepted 阶段进入普通表达、`expression_intent`、world-life Scene 选择上下文和 `GET /api/life/world` 的 `role_context`，重启后恢复。

方向证据分为 `support/conflict/neutral`：冲突降低净分但保留为反证，中性只审计，只有 support 计入最小数量和来源门槛；旧事件缺少 polarity 时兼容为 support。有限的中文 cue 邻接否定识别只用于用户 `dialogue/user_profile`，不把天气或世界事件的自然语言擅自判成反对。自动提案目前要求支持证据落在至少两个 UTC 事件日期；事件日期来自 `occurred_at`，缺失时回退 `observed_at`，并非 canonical world `logical_time` 的两日生活。这是当前实现边界，不代表角色已经真实跨日成长。

另一条独立链路把合格外部 observation 转成世界候选。候选仅包含服务端白名单动作，`preview` 不写 canonical world，只有显式 `accept` 才检查 world revision 并经统一 ingest/ledger 写入；没有可视化候选面板，也没有新的自动新闻 provider。角色方向候选不能直接改世界，世界候选也不能直接改变角色身份。

**G4：** 一个候选的证据、试行记录、确认/拒绝理由和旧阶段档案可完整回放；世界环境未经世界行动不变。

本次 P4 服务端自动化专项：role polarity 与跨 UTC 事件日期提案门槛定向测试 `13/13` 通过；完整 Node service 回归 `266/266` 通过，覆盖显式试行、候选/提案幂等、proposal decision 原子提交、accepted 投影、world candidate preview/accept 和 SQLite 重启恢复。`244/244` 保留为本轮增量前的历史快照。服务端规则通过不等于产品体验 gate 通过；真实 DeepSeek 的长周期人格体感、跨天主动提出新方向和候选处置体验仍需人工验收。

## P4.1：候选可见性、日期语义与纵向体验验收（当前下一步）

**目的：** 让用户和开发者能看见“哪些输入正在影响喵呜的方向”与“哪些外部事件可能改变世界”，并确认它们不会互相越权。

实施顺序：

1. 先重跑完整 Node service 回归，记录精确总数；不以专项 13/13 替代全量测试。
2. 为角色方向和世界候选提供清楚的观测/处置入口：显示来源、发生/观测时间、support/conflict/neutral、候选状态和提案依据；世界候选要显示动作白名单、preview、expected revision、accept/dismiss 结果。preview 必须无副作用，accept 才能写 canonical mutation。
3. 明确“跨日”产品语义：区分现实 UTC observation date 与虚拟世界 canonical logical day；决定角色方向积累究竟按哪种时间轴计量，并用固定时区、时钟边界、缺失时间和重放测试锁定行为。当前不能把 UTC 日期称作虚拟世界生活日。
4. 用隔离数据库走通 observation -> world candidate -> preview -> accept/dismiss -> mutation/evidence 回查，不注入正式存档，不调用付费或不必要的外部新闻 API。
5. 做至少 7 天的可回放纵向样本：方向证据有支持、冲突、中性和沉降；检查候选合并/淘汰、主动提议、`try/later/reject`、试行阶段表达是否有明显体感且不机械重复。真实模型样本和自动模拟结果分开记录。

**G4.1：** 全量回归通过；日期规则有明确产品决定且边界测试固定；候选面板/验收入口可完成只读观察与明确处置；外部 observation 不能直接改变世界，重复接受不能重复写入；7 日回放能从原始 evidence 解释角色提案，且不把“候选”误报为已改变身份。
