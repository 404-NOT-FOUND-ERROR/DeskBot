# DeskBot 视觉与角色语言迁移决策 v0.1

**日期：** 2026-09-18
**范围：** 桌面潮玩定位、聚形域持续世界、WorldOS 式世界观察、Character.AI 式沉浸故事的统一表现。
**状态：** 软件客户端与角色作者层的设计约束；不是最终工业设计、固件承诺或对参考品牌素材的复制许可。

## 1. 设计结论

DeskBot 采用 **“有触感的潮玩世界 + 克制的前沿 HUD”**，而不是完整复制任何一个参考对象。

```text
潮玩生命感       → Labubu 方法：强轮廓、爱憎、朋友/族群、变体是生活方式
持续世界结构     → WorldOS 方法：地点、时间、状态、NPC、事件和地图可观察
第一人称沉浸     → Character.AI 方法：Character/Soul、Scene、Lorebook、示例对白
电子前沿界面     → Marathon/GCORE/CSRC 方法：网格、非对称、模块、信息层级、状态信号
DeskBot 最终形态 → 木桌/软材质/摆件零件 + 少量高对比 HUD 标签 + 角色化中文叙事
```

参考资料：

- [Marathon 官方站](https://www.marathonthegame.com/zh-chs)：区域、赛季、外壳配置、探索风险、阵营合约和信息化世界展示。
- [GCORE：我尝试用《马拉松》的风格，做了一个信息展示网页](https://www.gcores.com/articles/200272)：Graphic Realism、瑞士现代主义、网格、无衬线、非对称、留白和强品牌色的方法总结。
- [CSRC Concept](https://csrc-concept.vercel.app/)：模块化首页、明确层级、导航分区、内容卡片和强 CTA 的信息组织参考。
- [Character.AI Creator Guide](https://support.character.ai/hc/en-us/articles/50608794517915-1-Welcome-to-the-Creator-Guide)、[Scene](https://support.character.ai/hc/en-us/articles/41918454359451-Scene-Creation-Quickstart-Guide)、[Lorebooks](https://support.character.ai/hc/en-us/articles/52739596326811-Lorebooks)：角色卡、场景和按相关性召回资料的方法参考。

## 2. 哪些适合迁移

### 2.1 从 Labubu / 潮玩角色迁移

- **强视觉锚点：** 当前喵呜保留白色多瓣底座、黑色圆屏、短三角耳和黄色胸口点，用户应能在小尺寸上认出它。
- **爱憎先于职业：** 角色卡必须写喜欢、讨厌、害怕、想要什么，以及什么事情会让它拒绝，而不是只有“职业/功能”。
- **关系构成世界：** NPC 不只是地图上的可点击按钮，要有朋友、竞争、误会、照顾和各自的生活圈。
- **变体是生活方式：** 新外壳不是随机换皮；它代表喵呜想体验的生活方向，必须有持续证据、试行和阶段记录。
- **奇怪但善良：** 可以调皮、猎奇、任性、主动，但不能用故弄玄虚或无理由拒绝替代人格。

不迁移：Labubu/ZIMOMO/MOKOKO 等角色名称、外形、故事或任何受保护视觉资产。这里只迁移角色系统方法。

### 2.2 从 Marathon / GCORE / CSRC 迁移

- **网格和模块：** 页面有固定层级：故事、地图、人物、世界、现实输入、研究台；不让所有信息同时抢第一屏。
- **非对称构图：** 地图做满屏舞台，左上故事卡、右侧人物卡、底部输入条形成可识别的阅读路径。
- **状态标签：** 地点、事件、抵达、可行动提示使用短标签和颜色信号；标签解释状态，不朗读数据库字段。
- **信息与氛围并置：** 大图/场景负责吸引，卡片负责可读，短 CTA 负责下一步；不要把背景故事全部挤进一张文字卡。
- **前沿感来自纪律：** 使用克制的无衬线、细线、编号、留白和对比色，而不是到处堆发光、噪声、扫描线或随机英文。
- **世界有不完整信息：** 可以保留未知、残缺记录和未解钩子，但必须用具体物件、任务或关系承载，不用抽象术语填空。

不迁移：Marathon 的军事科幻、武器/殖民地语汇、品牌标志、角色和图片素材。DeskBot 的核心情感是桌边共同生活，不是生存射击或战术撤离。

## 3. DeskBot 视觉系统

### 3.1 材质与色彩

| 层 | 视觉语言 | 用途 |
|---|---|---|
| 世界舞台 | 木桌、毛毡、软塑、纸片、布路线、树脂摊位 | 让地图看起来是可摆放、可触碰的桌面摆件 |
| 角色锚点 | 白色圆润外壳、黑屏、黄色点、短耳 | 让喵呜始终可认；形态变更也保留连续身份 |
| 前沿 HUD | 深墨、青绿、珊瑚/黄的短标签和细线 | 只表示地点、状态、风险、抵达和可操作入口 |
| 故事层 | 温暖的浅底、较大中文正文、短段落、物件插图 | 让第一人称叙事可读、有停顿、有关系感 |
| 研究层 | 深色、等宽字体、原始字段、revision、mutation | 只在研究开关打开后出现 |

### 3.2 三层界面

1. **游玩层：** 地图、喵呜故事、当前 Scene、人物入口、底部输入。用户不需要理解 schema、provider、证据或 role proposal。
2. **故事层：** NPC 对话、共同经历、地点旅记、可选的小行动。每个按钮都应像“做一件事”，而不是“调用接口”。
3. **研究层：** 多源输入、世界线编辑、记忆、方向试行、mutation ledger、原始状态。技术字段可以存在，但不应该污染第一屏。

## 4. 角色与 NPC 作者卡合同

每个角色 Markdown 卡至少要有：

```text
身份锚点 / 外形锚点
想要什么 / 喜欢什么 / 讨厌什么 / 害怕什么
与其他角色的关系
说话节奏、口癖、触发点、示例对白
当前 Scene 钩子
可以拒绝什么 / 不做什么
```

运行时流程：

```text
作者 Markdown
  → 校验后的 Persona 投影
  → 当前地点 + 已发生 Scene + 关系阶段 + 共同经历
  → LLM 只生成这一轮角色台词
  → Node 写入关系和共同经历
```

示例对白是高权重行为约束。抽象形容词只能说明方向，不能替代“它在什么场景下会说什么”。

运行时台词合同：正文默认控制在 `60-180` 个中文字符、`1-2` 个短段落，允许“一句动作描写 + 当面对白”。每轮必须自然包含直接回应、一个眼前物件或动作、人物判断和一个可继续的小选择；过短、过长、三段以上、客服化或只有抽象设定的草稿需要改写，二次仍不合格则回退作者台词。

## 5. 可读奇幻的内容规则

- 普通人能理解角色正在做什么。优先写纽扣、杯子、地图、路标、叶筒、摊灯、桌面和脚边动作。
- 一次回复最多让一个世界专有对象成为重点，并同时给出一个可见动作、物件或选择。
- 用户没有主动问世界观时，不解释光粒、光域、凝聚、漂移、影子等术语；它们是角色生活常识，不是科普词。
- 不把用户情绪强行写成外界异象；先回应人，再决定是否提到 Scene。
- `opportunity` 和 `unresolved_hook` 是可能性，不是已经发生的事实。
- 功能信息必须长在角色嘴里：天气、步骤、提醒和路线先完成事实，再以角色的判断、偏好和关系表达一次说完。
- NPC 可以拒绝、犹豫、误会和提出自己的小愿望；不能每轮同意，也不能变成客服。

## 7. 验收标准

每次新增地图或角色内容至少检查：

1. 1440px 第一屏是否一眼能看出是桌面摆件世界，而不是后台地图。
2. 用户是否能在 5 秒内找到喵呜、当前 Scene、输入框和当地人物。
3. NPC 回复是否在 60-180 个中文字符、1-2 个短段落内，同时包含直接回应、具体物件/动作、明确立场和一个可继续的小选择。
4. 普通聊天是否不需要理解聚形域术语也能读懂。
5. 研究字段是否只在研究层出现。
6. 角色、世界事实和地图移动是否仍由 canonical state 与 mutation 控制。

## 8. 可执行设计 token（v0.2）

这些 token 是当前 Web 实现的审查基线。它们服务于“桌面潮玩 + 电子前沿信息层”，不代表最终工业设计。

### 8.1 配色

| Token | 值 | 用途 |
|---|---|---|
| `world.surface` | `#36B8BD` 与地图 SVG 的暖色材质 | 世界舞台、地点底色 |
| `world.paper` | `#FBFCF5` / `rgba(251,252,245,.92)` | 故事卡、地图检查器、人物卡 |
| `world.ink` | `#223F47` | 中文正文和标题 |
| `world.muted` | `#688185` | 辅助说明、时间、状态 |
| `hud.cyan` | `#198E91` / `#E8FAF2` | 可达、正常、确认 |
| `hud.violet` | `#7355D4` | 角色、世界线、研究入口 |
| `toy.coral` | `#E95369` | 当前地点、活跃状态、玩具跳色 |
| `toy.amber` | `#F5C879` | 小物件、提醒、未决选择 |
| `research.deep` | `#07101E` | 研究台和原始数据，不进入游玩层 |

颜色规则：一张游玩卡最多使用一个主色、一个状态色和一个潮玩跳色；不把所有状态都做成霓虹。当前地点用珊瑚色，世界可达性用青绿色，方向/人物用紫色，未知或等待用琥珀色。

### 8.2 字体与层级

| 层级 | 桌面尺寸 | 移动尺寸 | 规则 |
|---|---:|---:|---|
| 世界标题 | 18px / 650 | 15px / 650 | 只出现一次，使用中文名称 |
| 卡片标题 | 14px / 700 | 13px / 700 | 不超过一行 |
| 故事正文 | 14px / 1.75 | 12px / 1.7 | 每段 1–3 句，保留停顿 |
| 辅助信息 | 10–11px / 1.5 | 9–10px / 1.45 | 只补充时间、地点、状态 |
| HUD / revision | 8–10px / 等宽 | 8–9px / 等宽 | 只用于短标签和审计字段 |

标题和正文使用 `Segoe UI`, `Microsoft YaHei`, `system-ui` 回退；等宽字体只用于状态编号、revision、schema，不用于角色对白。

### 8.3 间距与形状

- 基础间距为 `4/8/12/18/24px`；故事卡内边距 16–20px，地图节点标签内边距 5–7px。
- 游玩层卡片圆角 8–10px，输入条 8px，角色头像和小物件可使用 12–16px；研究层继续使用 8px，避免“糖果 UI”。
- 边框使用 1px 半透明线；阴影使用“短硬边 + 柔和扩散”两层，模拟摆件落在桌面的重量，不使用大面积发光。
- 地图节点必须有一个可识别的实体图形（小屋、路标、摊位、叶片、水盘），文字只说明名称和当前状态。

### 8.4 布局比例

- 1440px：地图占满背景；左上故事卡宽度 360–390px；底部输入条宽度 520–560px；右侧人物/地点检查器宽度不超过 360px。
- 390px 移动宽度：故事卡和人物卡改为底部抽屉；输入条固定底部；地图保留至少 42vh 的可见区域。
- 首屏只展示“当前地点、当前 Scene、喵呜、同地 NPC、输入框”；天气、世界线、记忆、证据和原始字段进入抽屉或研究模式。

### 8.5 文案和视觉的共同验收

每个地点必须同时提供一个可触碰的摆件语义、一个具体生活动作和一个可继续的小选择。若只能用“光粒、能量、世界线、凝聚”等抽象词描述，则视为没有完成潮玩化；需要改写为路标、杯子、叶筒、邮包、纽扣、布带或桌面动作。
